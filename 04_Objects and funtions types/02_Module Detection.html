MODULE DETECTION

UNDERSTANDING HOW TYPESCRIPT SCOPES YOUR FILES

Part 1: The Core Problem

Module Detection is a TypeScript compiler concept that determines whether a .ts file is treated as a module or a script.

TypeScript needs to decide, for every file, whether it should be compiled as:

  • A module → variables/types are scoped to that file, you need import/export to share things.
  • A script → everything declared is added to the global scope, visible everywhere.
The Danger

Getting this wrong causes weird bugs — like two files accidentally declaring the same variable name and colliding globally, or import/export not behaving as expected.

Part 2: How Detection Works (Traditionally)

Before TS 4.7, a file was considered a module only if it contained at least one import or export statement. 

// fileA.ts
export const name = "Alice"; // has an export → treated as a MODULE
// fileB.ts
const name = "Bob"; // no import/export → treated as a SCRIPT (global scope!)

If both files existed in the same project, fileB.ts's name would leak into the global scope and could clash with other global scripts.

Part 3: The moduleDetection Compiler Option (TS 4.7+)

TypeScript introduced an explicit setting in tsconfig.json: 

{
  "compilerOptions": {
    "moduleDetection": "auto" // "legacy" | "auto" | "force"
  }
}

The Three Modes:

1. "legacy"

Old behavior — a file is a module only if it has import/export.

2. "auto" (default)

Same as legacy, plus two extra cases:

  • If the file is a module format based on module setting (e.g., ESM-detected via package.json "type": "module").
  • If the file is a JSX file under certain conditions, or explicitly recognized as ESM by the environment.

3. "force"

Every file is treated as a module, regardless of whether it has import/export. This is the safest option for larger codebases. 

{
  "compilerOptions": {
    "moduleDetection": "force"
  }
}
// fileB.ts — no import/export, but still scoped as a module because of "force"
const name = "Bob"; // safe, private to this file

Why It Matters

Setting File with no import/export Risk
legacy / auto Treated as script → global scope Naming collisions across files
force Treated as module → file scope Safe, predictable
Quick Rule of Thumb
  • Writing a library or app with many files? Use "force" to avoid accidental global leaks.
  • Working with old-style global scripts (like ambient .d.ts declaration files without imports)? Keep "auto" or "legacy" so they stay global on purpose.

Bonus: Forcing a Single File to Be a Module

Even without changing tsconfig.json, you can force any individual file to be treated as a module by adding an empty export: 

export {};

This tells TypeScript "treat this file as a module" without actually exporting anything — a common trick in older codebases.

Part 4: Concrete Example (Collision Prevention)

Let's make it concrete with an actual bug to illustrate force's collision prevention benefits.

The Problem "force" Solves

Imagine you have two files, and neither one uses import or export: 

// counter.ts
let count = 0;
function increment() {
  count++;
}
// user.ts
let count = "Alice"; // 👈 same name, different type!
function getUser() {
  return count;
}

With moduleDetection: "legacy" (or "auto" without any module signals), both files are treated as scripts, meaning they share the same global scope — as if you pasted them into one big file.

Result: 💥

Cannot redeclare block-scoped variable 'count'.

TypeScript throws an error because count is declared twice globally. Even though these are two completely unrelated files that were never meant to interact, they collide.

With "force"

{
  "compilerOptions": {
    "moduleDetection": "force"
  }
}

Now every file — even ones without import/export — is automatically treated as its own isolated module. So: 

// counter.ts
let count = 0; // scoped to counter.ts only

// user.ts
let count = "Alice"; // scoped to user.ts only — totally fine!

No error. No collision. Each file has its own private scope, just like you'd expect in any modern JS/TS project.

Why This Matters in Practice

  • Safety by default — you don't have to remember to add export {} to every new file to avoid leaking into globals.
  • Prevents "invisible" bugs — without force, a file might accidentally start colliding with another file the moment someone adds a matching variable name — a bug that's easy to miss in large codebases.
  • Matches real-world JS behavior — modern bundlers (webpack, esbuild, Vite) already treat every file as a module. "force" makes TypeScript's mental model match what actually happens at runtime.
  • Useful for isolated tooling — TS's isolatedModules and transpile-per-file tools (like esbuild, SWC, Babel) compile one file at a time and can't see other files to know if something is a module or script. "force" guarantees consistent behavior since every file is unambiguously a module.

Simple Mental Model

Without force: "Is this file a module? Let me check if it has import/export..." 
               (fragile, depends on content)

With force:    "Every file is a module. Period." 
               (predictable, no guessing)
