Part 1: What is a Constraint? (Clear Definition)

The Definition

A constraint is a rule that limits what types can be used as a generic parameter. It tells TypeScript: "Only accept types that have these specific properties or methods."

The Simple Explanation

// ❌ Without constraint: T can be ANYTHING
function getLength<T>(value: T): number {
    return value.length; // ❌ ERROR! T might not have 'length'
}

// ✅ With constraint: T MUST have a 'length' property
function getLength<T extends { length: number }>(value: T): number {
    return value.length; // ✅ WORKS! TypeScript knows T has length
}

Let’s reset completely and build this from scratch, very slowly.

We’ll focus on this function:

function genLength2<T extends { length: number }>(value: T): number {
  return value.length;
}

and your call:

const res3 = genLength2({ length: 53325 });

You’re asking:

  • What does the constraint mean?
  • Is it applied to the value we pass, or the type?
  • What exactly is this “type” in practice?

Step 1: Separate “value” vs “type”

In TypeScript, there are always two layers:

  • Value: the actual thing at runtime (e.g. 123, "arman", { length: 53325 }).
  • Type: the description the compiler uses (e.g. number, string, { length: number }).

Example:

const x = 5;
// value of x: 5
// type of x: number

const y = { length: 53325 };
// value of y: { length: 53325 }
// type of y: { length: number }

So when you call:

genLength2({ length: 53325 });

You pass a value: { length: 53325 }.
TypeScript infers a type from that value: { length: number }.
The constraint always checks the type, not the raw value.

Step 2: What does T extends { length: number } mean?

Think of it like a rule:
“Whatever T is, it must have a length property of type number.”

That { length: number } is just a type describing a shape:
“An object/type that has at least a length property that is a number.”

So:

function genLength2<T extends { length: number }>(value: T): number {
  return value.length;
}

reads as:

  • T is a generic type parameter.
  • T is restricted to types that have length: number.
  • value is of type T.

Inside the function, we are allowed to do value.length because the compiler knows length exists on T.

Step 3: How the call is checked

Call:

const res3 = genLength2({ length: 53325 });

Compiler process:

  1. Look at the value { length: 53325 }.
  2. Infer its type: { length: number }.
  3. Ask: “Can this inferred type be used as T where T extends { length: number }?”

Since { length: number } obviously has length: number, the rule is satisfied, so the call is allowed.

If you tried:

genLength2(123);

Compiler process:

  1. Value: 123.
  2. Inferred type: number.
  3. Check: “Does type number satisfy the rule extends { length: number }?”

Answer: no, number does not guarantee a length property, so the call is rejected at compile time.

Step 4: So, is the constraint on the value or the type?

Short answer in your terms:

  1. You pass a value.
  2. TypeScript infers or uses a type for that value.
  3. The constraint is applied to that type.
  4. If the type fits the constraint, the value is accepted; if not, TypeScript gives a type error.

So when you say:
“during calling the function it must have written length property”

You can refine that to:
“during calling the function, the type of the value must have a length: number property”.

That’s why these work:

genLength2("hello");             // OK, type is string, and string has length: number
genLength2([1, 2, 3]);           // OK, type is number[], arrays have length: number
genLength2({ length: 53325 });   // OK, type has length: number

and these fail:

genLength2(123);     // type is number → no length: number
genLength2(true);    // type is boolean → no length: number

Part 2: Why We Need Constraints

The Problem: Without Constraints

// ❌ This function is unsafe
function logObject<T>(obj: T): T {
    console.log(obj.name); // ❌ ERROR: T might not have 'name'
    return obj;
}

// Why? Because T could be:
logObject({ name: "Alice" }); // ✅ Works
logObject(42); // ❌ 42 doesn't have 'name'
logObject("hello"); // ❌ "hello" doesn't have 'name'
logObject(true); // ❌ true doesn't have 'name'
logObject(null); // ❌ null doesn't have 'name'
logObject(undefined); // ❌ undefined doesn't have 'name'

The Solution: With Constraints

// ✅ This function is safe
function logObject<T extends { name: string }>(obj: T): T {
    console.log(obj.name); // ✅ WORKS! TypeScript knows T has 'name'
    return obj;
}

// Now only valid types work:
logObject({ name: "Alice" }); // ✅ Works
logObject({ name: "Bob", age: 25 }); // ✅ Works (has extra property)

// ❌ Invalid types fail:
logObject(42); // ❌ Error: number doesn't have 'name'
logObject("hello"); // ❌ Error: string doesn't have 'name'
logObject(true); // ❌ Error: boolean doesn't have 'name'

Part 3: Syntax of Constraints

Basic Syntax

function functionName<T extends ConstraintType>(parameter: T): T {
    // ...
}

Syntax Breakdown

function logObject<T extends { name: string }>(obj: T): T {
//               ↑
//               |
//           Constraint: T must have a 'name' property of type string
    console.log(obj.name);
    return obj;
}

Different Constraint Types

// 1. Constraint to a type
function process<T extends string>(value: T): T {
    return value;
}

// 2. Constraint to an interface
interface HasName {
    name: string;
}
function logName<T extends HasName>(obj: T): T {
    console.log(obj.name);
    return obj;
}

// 3. Constraint to a type alias
type Identifiable = { id: number };
function getById<T extends Identifiable>(obj: T): number {
    return obj.id;
}

// 4. Constraint to multiple requirements
type HasName = { name: string };
type HasAge = { age: number };
function logPerson<T extends HasName & HasAge>(obj: T): T {
    console.log(obj.name, obj.age);
    return obj;
}

Part 4: Constraints in the form of sets

1. Two kinds of constraints: shape vs set

So far you’ve seen shape constraints:

T extends { length: number }
T extends { id: string; name: string }

These say: “T must have at least these properties.”

There’s another very important way to think about constraints:

A generic type parameter can be constrained to a set of allowed types.

Informally, you can imagine:

T ∈ { string, number, boolean }

In TypeScript syntax, that “set of allowed types” is usually a union type: 

function parseId<T extends string | number>(id: T) {
  // T is allowed to be string OR number, nothing else
}

Here:

  • The set of allowed types for T is { string, number }.
  • If you try to pass a boolean, TypeScript rejects it because boolean is not in that set.

So:
“constraints in the form of sets” = “T can only be one of these specific types”.

2. Concrete example: constraint as a set

Look at this:

type AllowedStatus = "pending" | "success" | "failed";

function handleStatus<T extends AllowedStatus>(status: T) {
  // T must be one of "pending" | "success" | "failed"
}

Think of it like:

T ∈ { "pending", "success", "failed" }
  • If you call handleStatus("pending") → OK.
  • If you call handleStatus("foo") → Error, because "foo" is not in the allowed set.

Same idea with primitive types:

function logValue<T extends string | number | boolean>(value: T) {
  console.log(value);
}

Here, the allowed set is { string, number, boolean }.
Anything outside that set (like null or {}) is rejected.

3. Combining “set of types” with “shape”

You can mix both ideas:

Set of shapes

type HasId = { id: string };
type HasName = { name: string };

function printEntity<T extends HasId | HasName>(entity: T) {
  // T is either { id: string } OR { name: string } OR something that matches one of those
}

Here: The allowed set for T is types that look like { id: string } OR { name: string }.

Set of primitive types

function asString<T extends string | number>(value: T): string {
  return String(value);
}

Set for T = { string, number }.

This is very similar to how you might think about enums or finite allowed values, but at the type level.

4. Why “set” thinking is useful

Thinking in terms of sets helps you reason like this:

  • Unconstrained generic: T can be any type (the set of all possible types).
  • Constrained generic (shape): T is limited to types that have certain properties (subset of all types that have that shape).
  • Constrained generic (union/set): T is limited to a specific finite set of types: T ∈ { string, number }, or T ∈ { "pending", "success", "failed" }.

So when you write:

function fn<T extends A | B | C>(value: T) { ... }

you can mentally read:
“T must be one of the types in the set { A, B, C }.”

Part 5: The extends Keyword & Check Process

In TypeScript What It Means
T extends string T must be a subtype of string (string or a literal like "hello")
T extends object T must be an object
T extends { name: string } T must have a name property of type string
T extends keyof U T must be a key of U
T extends U T must be assignable to U

The Type Check Process

// Step 1: Define the function with constraint
function getLength<T extends { length: number }>(value: T): number {
    return value.length;
}

// Step 2: You call it with a string
getLength("hello");

// Step 3: TypeScript checks:
// Does string extend { length: number }?
// string has length: number → YES
// ✅ Allowed

// Step 4: You call it with a number
getLength(42);

// Step 5: TypeScript checks:
// Does number extend { length: number }?
// number does NOT have length → NO
// ❌ Error!

Part 6: Common Constraint Patterns

Pattern 1: Constraint to Object

// T must be an object
function logObject<T extends object>(obj: T): T {
    console.log(obj);
    return obj;
}

// Works:
logObject({ name: "Alice" }); // ✅
logObject([]); // ✅ (array is an object)
logObject(new Date()); // ✅

// Fails:
logObject("hello"); // ❌ string is not an object
logObject(42); // ❌ number is not an object

Pattern 2: Constraint to Specific Shape

// T must have a 'name' property
function logName<T extends { name: string }>(obj: T): T {
    console.log(obj.name);
    return obj;
}

// Works:
logName({ name: "Alice" }); // ✅
logName({ name: "Bob", age: 25 }); // ✅

// Fails:
logName({ age: 25 }); // ❌ missing 'name'
logName({ name: 42 }); // ❌ 'name' must be string

Pattern 3: Constraint with keyof

// K must be a key of T
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
}

const user = { name: "Alice", age: 25 };

getProperty(user, "name"); // ✅ Works: returns string
getProperty(user, "age"); // ✅ Works: returns number
getProperty(user, "email"); // ❌ Error: 'email' is not in user

Part 7: Unpacking typeof in Constraints

Let’s unpack this step by step.

1. What does typeof config mean here?

In a type position, typeof does not mean the JS runtime "string" | "number" thing.
Instead, it means “give me the TypeScript type of this variable.”

For your config, TypeScript infers a type like:

type ConfigType = {
  apiUrl: string;
  timeout: number;
  retries: number;
};

So:

typeof config  // is that object type above

So typeof config is just a type alias for “an object with apiUrl: string, timeout: number, retries: number”.

2. What does T extends typeof config mean?

Your generic function:

function getConfig<T extends typeof config>(value: T): T {
    return value;
}

reads as:

  • T is a generic type parameter.
  • T is constrained by extends typeof config.

So the rule is:
“Whatever type T is, it must be assignable to the type of config.”

In other words, T must at least have:

{
  apiUrl: string;
  timeout: number;
  retries: number;
}

It can be:

  • exactly that type, or
  • a more specific/narrow version (for example, stricter literals or extra properties, depending on settings).

3. Why each call behaves the way it does

Call 1

getConfig(config);

Type of config is typeof config.
So here T is inferred as typeof config.
That clearly satisfies T extends typeof config, so it works.

Call 2

getConfig({ apiUrl: "https://dev.com", timeout: 1000, retries: 1 });

TypeScript infers the type of that literal as something compatible with: 

{
  apiUrl: string;
  timeout: number;
  retries: number;
}

Even though the exact literal types might be "https://dev.com" | 1000 | 1, those are still assignable to string | number. So this object matches the shape of typeof config, and the constraint is satisfied.

Call 3

getConfig({ apiUrl: "https://dev.com" });

TypeScript infers the type as:

{
  apiUrl: string;
}

Now the compiler checks:
“Is { apiUrl: string } assignable to typeof config (which requires apiUrl, timeout, and retries)?”

Answer: no. It’s missing timeout and retries.
So T extends typeof config is not satisfied → compile-time error.

What is a Constructor? (The Foundation)

In JavaScript

A constructor is a function that creates an instance of a class.

// This is a constructor
class Person {
    constructor(name) {
        this.name = name;
    }
}

// You call it with 'new' to create an instance
const alice = new Person("Alice");
//           ↑
//           |
//      'new' calls the constructor

In JavaScript, A Constructor Is Just a Function

// A constructor function (old way)
function Person(name) {
    this.name = name;
}

// Same usage with 'new'
const alice = new Person("Alice");

The Role of new

When you use new What happens
new Person("Alice") 1. Creates a new empty object
2. Calls the constructor with this = new object
3. Returns the new object

The Problem (Without Constructor Constraints)

Scenario: Creating Instances from a Class

// You have a class
class Person {
    name: string;
    constructor(name: string) {
        this.name = name;
    }
}

// You want a function that creates an instance
function createInstance(ctor: any, ...args: any[]): any {
    return new ctor(...args);
}

const alice = createInstance(Person, "Alice");
// ❌ TypeScript doesn't know what this returns
// ❌ TypeScript doesn't know what 'ctor' should be
// ❌ No type safety!

The Problem Explained

// ❌ This function accepts ANYTHING
function createInstance(ctor: any, ...args: any[]): any {
    return new ctor(...args);
}

// This works:
createInstance(Person, "Alice"); // ✅

// But this ALSO compiles:
createInstance(42, "Alice"); // ❌ Runtime error! 42 is not a constructor
createInstance("hello", "Alice"); // ❌ Runtime error! "hello" is not a constructor
createInstance(null, "Alice"); // ❌ Runtime error! null is not a constructor

// TypeScript allows all of these because 'any' disables type checking

Part 9: The Solution (Constructor Constraints)

What is a Constructor Constraint?

Definition: A constructor constraint is a rule that says: "T must be a class/constructor that can be called with new."

The Syntax

function createInstance<T>(ctor: new (...args: any[]) => T, ...args: any[]): T {
    return new ctor(...args);
}
//                    ↑
//                    |
//              This is the constraint!

Breaking Down the Syntax

new (...args: any[]) => T
// ↑      ↑          ↑
// |      |          |
// |      |          Returns an instance of T
// |      The constructor takes any number of arguments
// Must be callable with 'new'

Complete Syntax Breakdown

function createInstance<T>(
    ctor: new (...args: any[]) => T,
    //   ↑          ↑          ↑
    //   |          |          |
    //   |          |          Returns T
    //   |          Takes any number of arguments
    //   Must be callable with 'new'

    ...args: any[]
    //     ↑
    //     |
    //     Arguments to pass to the constructor

): T {
    // ↑
    // |
    // Returns an instance of T

    return new ctor(...args);
}

Part 10: Introducing InstanceType & ConstructorParameters

By Little Re-Teaching of Constructor Constraints

1. What is a “constructor type”?

In JS/TS, a class has two “faces”:

class User {
  constructor(public name: string) {}
  greet() { console.log("hi"); }
}
  • As a value (runtime): User is a constructor function you can call with new User("arman").
  • As a type (compile time): User is the type of instances created by new User(...).

TypeScript has a way to describe “something you can call with new” at the type level: 

type UserCtor = new (name: string) => User;

Read this as:
“A constructor that takes a string and returns a User instance.”

That’s a constructor type.

2. Constraining a generic to “must be a constructor”

Say you want a function that only accepts constructors you can call with new: 

function make<T extends new (...args: any[]) => any>(Ctor: T) {
  return new Ctor(); // OK because T is guaranteed to be 'new'-able
}

Key points:

  • T is a type parameter.
  • T extends new (...args: any[]) => any means: “T must be a type that has a construct signature.”
  • In plain language: “T must be something you can do new T(...) on.”

Now calling:

class Service {}
make(Service); // OK: Service has a constructor
make(123);     // Error: number is not a constructor

So constructor constraint = T extends new (...args: any[]) => Something.

You can also restrict arguments:

function makeUser<T extends new (name: string) => any>(Ctor: T) {
  return new Ctor("arman");
}

This now says:
“T must be a constructor that takes a single string parameter.”

3. Where InstanceType and ConstructorParameters come in

Once you are comfortable with “T is a constructor”, two common questions appear:

  • “What is the type of the instance I get from this constructor?”
  • “What are the types of the constructor’s parameters?”

TypeScript has built-in utility types to answer exactly those:

  • InstanceType<TCtor> → the instance type produced by constructor TCtor.
  • ConstructorParameters<TCtor> → the constructor argument types as a tuple.

3.1. Example with a class

class Logger {
  constructor(public level: "info" | "error") {}
  log(msg: string) {}
}

At type level:

  • typeof Logger is the constructor type: new (level: "info" | "error") => Logger.
  • Logger (without typeof) is the instance type.

Now:

type LoggerInstance = InstanceType<typeof Logger>;         // Logger
type LoggerArgs = ConstructorParameters<typeof Logger>;    // [level: "info" | "error"]

InstanceType<typeof Logger> extracts “what new Logger(...) returns” → Logger.

ConstructorParameters<typeof Logger> extracts “what parameters the constructor takes” → a tuple ["info" | "error"].

So these utilities just read information out of the constructor type.

3.2. Putting it together: a generic factory

Now combine everything:

function make<T extends new (...args: any[]) => any>(
  Ctor: T,
  ...args: ConstructorParameters<T>  // use whatever args that constructor expects
): InstanceType<T> {                 // return the correct instance type
  return new Ctor(...args);
}

Line by line:

  • T extends new (...args: any[]) => any
    Constraint: T must be a constructor.
  • Ctor: T
    The actual constructor passed in.
  • ...args: ConstructorParameters<T>
    “The args you pass must match the constructor parameters of T.”
  • : InstanceType<T>
    “The function returns whatever instance type that constructor creates.”

Usage:

class User {
  constructor(public name: string) {}
}

const u = make(User, "Arman"); // u: User

This is just type-level plumbing to avoid repeating name: string or User manually.

Second RealWorld Example

class User {
    constructor(
        public id: number,
        public name: string,
        public email: string
    ) { }
}

class Product {

What constraints are Rules that limit what types can be used
Why we need them To safely access properties/methods
Syntax <T extends { property: type }>
The new constraint new (...args: any[]) => T
keyof constraint <K extends keyof T>
Multiple constraints <T extends A & B>
The 1% Realization

"A constraint doesn't ADD anything to T. It REQUIRES T to already have something." 

// ❌ Wrong mental model:
// "I'm adding a 'length' property to T"
function getLength<T extends { length: number }>(value: T): number {
    return value.length;
}

// ✅ Correct mental model:
// "I'm telling TypeScript: T MUST already have 'length'"
// "Only allow types that have 'length'"
// "Then I can safely access value.length"
