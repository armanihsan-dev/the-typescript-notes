UNIONS & INTERSECTIONS

THE 1% DEVELOPER KNOWLEDGE: UNLOCKING THE DEEP, HIDDEN WORLD OF TYPE BEHAVIOR

Part 1: The 1% Truth

You already know the basics: | for union, & for intersection. But there's a deep, hidden world of union/intersection behavior that most developers never discover. Let's unlock that.

The Core Secret

Unions distribute over intersections, but intersections don't distribute over unions.

Most developers don't even know this is a thing. Here's what I mean:

// ✅ Union distributes over Intersection
type Result1 = (A | B) & C;  // = (A & C) | (B & C)

// ❌ Intersection does NOT distribute over Union
type Result2 = (A & B) | C;  // NOT equal to (A | C) & (B | C)

Explanation of Distribution

First, think of:

  • | (union) = OR
  • & (intersection) = AND

For example:

type A = { a: number }
type B = { b: string }
type C = { c: boolean }

What does "union distributes over intersection" mean?

Just like in algebra:

x & (y | z) = (x & y) | (x & z)

In TypeScript:

type Result = A & (B | C)

TypeScript automatically treats this as:

type Result = (A & B) | (A & C)

So instead of saying:
"An object with a AND either b or c"
It becomes:
"Either: an object with a and b OR an object with a and c"

Example

type X = { a: number }
type Y = { b: string }
type Z = { c: boolean }

type T = X & (Y | Z)

// TypeScript sees this as
type T =
    | { a: number; b: string }
    | { a: number; c: boolean }

// Both are valid:
const t1: T = {
    a: 1,
    b: "hello"
}

const t2: T = {
    a: 1,
    c: true
}

But intersections DON'T distribute over unions

Suppose we start with:

type T = (A & B) | C

TypeScript doesn't rewrite it into:

(A | C) & (B | C)   // ❌ Not what TypeScript does

It simply stays:

(A & B) | C

Why? Because distributing it changes the meaning.

Imagine:

type A = { a: number }
type B = { b: string }
type C = { c: boolean }

Original: (A & B) | C means:

{ a, b }
OR
{ c }

If we distributed: (A | C) & (B | C), that expands into:

(A & B)
|
(A & C)
|
(C & B)
|
(C)

Notice all these extra possibilities: { a, c } and { b, c }. Those were not allowed in the original type. So distribution would change the meaning, which is why TypeScript doesn't do it.

A visual way to remember

Think of intersection (&) as attaching something to every option in a union.

A & (B | C)

        B
      /
A ----
      \
        C

Attach A to every branch:
(A & B) | (A & C)

But going backwards: (A & B) | C, there's no common thing you can safely pull out.

Real-world example

type Success = {
    ok: true
    data: string
}

type Error = {
    ok: false
    message: string
}

type Timestamp = {
    createdAt: Date
}

// Now:
type Response = Timestamp & (Success | Error)

// becomes
type Response =
    | (Timestamp & Success)
    | (Timestamp & Error)

// which is
type Response =
    | {
        createdAt: Date
        ok: true
        data: string
      }
    | {
        createdAt: Date
        ok: false
        message: string
      }

Every response has a timestamp, regardless of whether it's a success or an error.

The Key Takeaway

✅ A & (B | C) becomes (A & B) | (A & C) — intersections distribute across unions.

❌ (A & B) | C does not become (A | C) & (B | C) — because that would introduce new, unintended type combinations and change the meaning.

Part 2: The Distributive Law in TypeScript

2.1 Union over Intersection (Distribution Works)

type A = { a: string };
type B = { b: number };
type C = { c: boolean };

// ✅ Union distributes over intersection
// (A | B) & C = (A & C) | (B & C)

type Left = (A | B) & C;
// Left = { a: string; c: boolean } | { b: number; c: boolean }

type Right = (A & C) | (B & C);
// Right = { a: string; c: boolean } | { b: number; c: boolean }

// Left and Right are IDENTICAL!
// TypeScript handles this automatically

2.2 Intersection over Union (Distribution DOES NOT Work)

type A = { a: string };
type B = { b: number };
type C = { c: boolean };

// ❌ Intersection does NOT distribute over union
// (A & B) | C ≠ (A | C) & (B | C)

type Left = (A & B) | C;
// Left = { a: string; b: number } | { c: boolean }

type Right = (A | C) & (B | C);
// Right = { a: string; b: number; c: boolean } | { a: string; c: boolean } | { b: number; c: boolean }

// Left and Right are NOT the same!

Part 3: The "Never" Trap (1% Knowledge)

3.1 Intersecting with never = never

// ❌ Most developers think this would work
type A = string & number;
// A = never (no value can be both string AND number)

// ✅ But what about:
type B = { name: string } & { name: number };
// B = { name: never }
// The 'name' property is never

// 🧠 1% knowledge: This creates a property that can't exist
function test(obj: B) {
    obj.name; // Type: never
    // You can't assign anything to obj.name
    // obj.name = "hello"; // ❌ Type 'string' is not assignable to type 'never'
}

3.2 The Real-World "Never" Trap

// Most developers write this and get confused:
type ApiResponse = {
    data: string;
} & {
    data: number;
};

// Response = { data: never }

// They expected: data to be string | number
// But got: data is never (impossible!)

// ✅ The correct way:
type ApiResponse = {
    data: string | number;  // Union on the property level
};

// Or:
type ApiResponse = 
    | { data: string }
    | { data: number };  // Union on the type level

Part 4: The Discriminated Union Pattern (1% Pattern)

4.1 What Most Developers Do

// ❌ Common mistake: Checking without a discriminator
type Success = { data: string };
type Error = { error: string };
type Response = Success | Error;

function handle(res: Response) {
    // ❌ Can't tell which one it is!
    // if (res.data) // This works, but it's fragile
}

4.2 The 1% Way: Discriminated Unions

// ✅ The 1% pattern: Add a discriminator
type Success = {
    kind: "success";
    data: string;
};

type Error = {
    kind: "error";
    error: string;
};

type Response = Success | Error;

function handle(res: Response) {
    // ✅ TypeScript now knows exactly which one it is!
    if (res.kind === "success") {
        console.log(res.data); // ✅ Type-safe
    } else {
        console.log(res.error); // ✅ Type-safe
    }
}

4.3 The "Exhaustiveness Check" (1% Advanced)

type Loading = { kind: "loading" };
type Success = { kind: "success"; data: string };
type Error = { kind: "error"; error: string };

type State = Loading | Success | Error;

function handleState(state: State): string {
    switch (state.kind) {
        case "loading":
            return "Loading...";
        case "success":
            return state.data;
        case "error":
            return state.error;
        default:
            // 🔥 1% knowledge: Exhaustiveness checking
            const _exhaustive: never = state;
            return _exhaustive;
    }
}

// If you add a new state, TypeScript will error!
// type State = Loading | Success | Error | Idle;
// ❌ Error: Type 'Idle' is not assignable to type 'never'

Part 5: The "Union in Generic" Behavior (1% Knowledge)

5.1 What Most Developers Think

// Most think this works the same:
type Result = T extends string ? "Yes" : "No";

type Test1 = Result<"hello">; // "Yes"
type Test2 = Result<"hello" | "world">; // "Yes" (they think)

5.2 What Actually Happens (The 1% Truth)

// 🔥 Naked type parameters DISTRIBUTE over unions!
type Result = T extends string ? "Yes" : "No";

type Test1 = Result<"hello">; // "Yes"
type Test2 = Result<"hello" | "world">; // "Yes" | "Yes" = "Yes"

// ✅ Wait, that's the same? Let's try with mixed:
type Test3 = Result<"hello" | 42>; 
// ✅ "Yes" | "No" (not just "No"!)

// Why? Because the conditional DISTRIBUTES:
// ("hello" extends string ? "Yes" : "No") | (42 extends string ? "Yes" : "No")
// = "Yes" | "No"

Part 6: The "Intersection of Functions" Behavior (1% Knowledge)

6.1 Most Developers Think

// Most think this creates a function that can do both:
type A = (x: string) => void;
type B = (x: number) => void;

type C = A & B;

// They think: C can take string OR number
// ❌ WRONG!

6.2 The 1% Truth

// 🔥 Intersection of functions creates an OVERLOAD
type A = (x: string) => void;
type B = (x: number) => void;

type C = A & B;

// C = { (x: string): void; (x: number): void }
// This is an overloaded function!

const c: C = (x: string | number) => {
    console.log(x);
};

c("hello"); // ✅ Works
c(42);      // ✅ Works
c(true);    // ❌ Error: Argument of type 'boolean' is not assignable to parameter of type 'string & number'

The 1% truth: TypeScript's union and intersection types follow the rules of set theory exactly. Understanding this reveals:

  • Never absorption - Why never disappears in unions and dominates in intersections
