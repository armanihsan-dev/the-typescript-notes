What is meant by Configuring the TypeScript Compiler?

What is "Configuring the TypeScript Compiler"?

Definition: Configuring the TypeScript compiler means creating and customizing a tsconfig.json file that tells the TypeScript compiler (tsc) exactly how to behave when it processes your code.

What You're Actually Doing When You Configure

When you configure the TypeScript compiler, you're answering these questions:

Question What it controls
Which files to compile? include, exclude, files
Where to put the output? outDir, rootDir
What JavaScript version? target (ES5, ES6, ES2020, etc.)
What module system? module (CommonJS, ESModules, etc.)
How strict to be? strict, noImplicitAny, strictNullChecks
What extra features? jsx, resolveJsonModule, sourceMap
What to do on errors? noEmitOnError, skipLibCheck

5. What is tsconfig.json? Purpose, Need, and Effect

Definition

tsconfig.json: A configuration file that tells the TypeScript compiler how to behave, which files to process, and what output to generate.

Purpose

Serves as the single source of truth for TypeScript compilation settings across your entire project.

Need (Why can't I just use command-line flags?)

Without tsconfig.json With tsconfig.json
Must type tsc app.ts --target es2020 --outDir dist --strict every time Simply run tsc
Settings lost when terminal closes Settings persisted in file
Each developer uses different settings All developers use same settings
Build tools (webpack, Vite) don't know your settings Build tools read tsconfig.json automatically
Can't manage large projects efficiently Essential for multi-file projects

tsconfig.json Structure

{
  "compilerOptions": {
    // Compilation behavior
  },
  "include": [
    // Files to compile
  ],
  "exclude": [
    // Files to ignore
  ]
}

Common compilerOptions Explained

{
  "compilerOptions": {
    /* Output Settings */
    "target": "ES2020",        // Which JavaScript version to output
    "module": "commonjs",      // Module system for Node.js
    "outDir": "./dist",        // Where to put compiled .js files
    "rootDir": "./src",        // Where to look for .ts files

    "pretty": true, // logs the error pretty

    "declaration": true,       // Generate .d.ts files
    "sourceMap": true,         // Generate .js.map files for debugging
    
    /* Strict Settings */
    "strict": true,            // Enables ALL strict type checking
    "noImplicitAny": true,     // Error if type can't be inferred
    "strictNullChecks": true,  // null and undefined separate types
    "strictFunctionTypes": true,
    "strictPropertyInitialization": true,
    
    /* Module Resolution */
    "esModuleInterop": true,   // Better CommonJS/ES module compatibility
    "resolveJsonModule": true,  // Allow importing JSON files
    "allowSyntheticDefaultImports": true,
    
    /* Linting */
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    
    /* Source Files */
    "allowJs": true,           // Allow compiling .js files too
    "checkJs": true,           // Type-check .js files
    "jsx": "react"             // Support JSX syntax
  },
  
  "include": [
    "src/**/*.ts",             // All .ts files in src folder
    "src/**/*.tsx"             // All .tsx files
  ],
  
  "exclude": [
    "node_modules",            // Ignore dependencies
    "dist",                    // Ignore output folder
    "**/*.test.ts"             // Ignore test files
  ]
}

Effect (What actually changes)

Without tsconfig.json:

tsc app.ts          # Compiles app.ts to app.js in same directory

With tsconfig.json:

tsc                 # Compiles ALL files matching include pattern
                    # Outputs to outDir directory
                    # Uses target, module, and all other settings
                    # Applies strict type checking
                    # Generates source maps

Strict Mode in TypeScript - Complete Guide

1. What is Strict Mode?

Definition: Strict mode is a collection of compiler flags that enable the highest level of type safety in TypeScript. When enabled, the compiler performs aggressive type checking to catch more potential bugs at compile time.

The "strict": true flag is a shortcut that enables all strict family checks with a single setting.

2. What "strict": true Actually Enables

When you set "strict": true in tsconfig.json, TypeScript automatically enables all of these checks: 

{
  "compilerOptions": {
    "strict": true  // This ONE line enables ALL below:
    // "noImplicitAny": true
    // "strictNullChecks": true
    // "strictFunctionTypes": true
    // "strictBindCallApply": true
    // "strictPropertyInitialization": true
    // "noImplicitThis": true
    // "alwaysStrict": true
  }
}

3. Detailed Explanation of Each Flag

A. "strictNullChecks": true

Definition: When enabled, null and undefined are treated as distinct types and cannot be assigned to other types without explicit handling.

Without strictNullChecks (false):

// This code compiles without errors
let name: string = "Arman";
name = null;    // ✅ No error - This is dangerous!
name = undefined; // ✅ No error - Also dangerous!

let age: number = 25;
age = null;     // ✅ No error
age = undefined; // ✅ No error

The problem: You can assign null or undefined to any variable, leading to runtime errors: 

let name: string = "Arman";
name = null;

// Later in your code...
console.log(name.toUpperCase()); 
// ❌ RUNTIME ERROR: Cannot read property 'toUpperCase' of null

With strictNullChecks (true):

let name: string = "Arman";
name = null;     // ❌ Error: Type 'null' is not assignable to type 'string'
name = undefined; // ❌ Error: Type 'undefined' is not assignable to type 'string'

// ✅ Correct way: Use union types
let name2: string | null = "Arman";
name2 = null;    // ✅ Allowed - we explicitly said it can be null

// ✅ Correct way: Check before using
if (name2 !== null) {
    console.log(name2.toUpperCase()); // ✅ Safe
}

// Or use optional chaining
console.log(name2?.toUpperCase()); // ✅ Safe - returns undefined if null

B. "noImplicitAny": true

Definition: When enabled, TypeScript will throw an error if it cannot infer the type of a variable or parameter and would otherwise default to any.

Without noImplicitAny (false):

// TypeScript can't infer the type of 'x'
function add(a, b) {
    return a + b;
}
// 'a' and 'b' are implicitly 'any' - No error!

let data; // Implicitly 'any' - No error!
data = 5;
data = "hello"; // Allowed because 'any'

The problem: any disables all type checking, defeating TypeScript's purpose: 

function add(a, b) {
    return a + b;
}

add("hello", 5);   // ✅ No error - but result is "hello5" (unexpected!)
add({}, []);       // ✅ No error - result is "[object Object]" (nonsense!)
// Runtime bugs are now your problem!

With noImplicitAny (true):

function add(a, b) {
    // ❌ Error: Parameter 'a' implicitly has an 'any' type
    // ❌ Error: Parameter 'b' implicitly has an 'any' type
    return a + b;
}

// ✅ Fix 1: Explicitly type the parameters
function add(a: number, b: number): number {
    return a + b;
}

// ✅ Fix 2: Use 'any' explicitly if you really need it
function add(a: any, b: any): any {
    return a + b;
}

// ✅ Fix 3: Let TypeScript infer from context
const add = (a: number, b: number) => a + b;

C. How "strict" Works Together

Real-world example showing how all flags work together:

// ❌ This code will FAIL with "strict": true

// 1. noImplicitAny catches this
function processUser(user) {  
    // ❌ Error: Parameter 'user' implicitly has an 'any' type
    return user.name;
}

// 2. strictNullChecks catches this
let username: string = "Arman";
username = null;  
// ❌ Error: Type 'null' is not assignable to type 'string'

// 3. strictPropertyInitialization catches this
class User {
    name: string;  
    // ❌ Error: Property 'name' has no initializer and is not definitely assigned
    // in the constructor
}

// 4. noImplicitThis catches this
function greet() {
    console.log(this.name);
    // ❌ Error: 'this' implicitly has type 'any'
}

Understanding the noImplicitThis Error

With strict mode true:

function Car(car: { name: string }) {
    console.log(this);
    console.log(car);
}

console.log(Car({ name: 'BMW' }));

.. this says: 'this' implicitly has type 'any' because it does not have a type annotation. .. what meant by the error a how to solve it?

What the Error Means

Error Message:

'this' implicitly has type 'any' because it does not have a type annotation.

Definition: TypeScript cannot determine what this refers to inside your function, so it would default to any. But because "strict": true enables noImplicitThis, TypeScript refuses to allow this to be any and forces you to explicitly declare its type.

Why This Error Happens

The Problem:

function Car(car: { name: string }) {
    console.log(this);  // ← What is 'this' here?
    console.log(car);
}

The issue: In JavaScript, this can refer to different things depending on how the function is called:

Call Context What this refers to
Car({ name: 'BMW' }) undefined (in strict mode) or global object
new Car({ name: 'BMW' }) Newly created instance
carObject.Car() The carObject itself
Car.call(someObject, { name: 'BMW' }) someObject

TypeScript cannot guess which one you mean, so it throws an error.

How to Fix It (3 Solutions)

Solution 1: Declare this Type Explicitly

Add a type annotation for this as the first parameter: 

function Car(this: any, car: { name: string }) {
    console.log(this);   // ✅ Now TypeScript knows 'this' is 'any'
    console.log(car);
}

console.log(Car({ name: 'BMW' }));
// Output: 
// undefined
// { name: 'BMW' }

The this parameter is a fake parameter — it doesn't exist at runtime. It's only for TypeScript.

Solution 2: Specify the Exact this Type

Instead of any, declare what this should actually be: 

// When 'this' is a specific object type
function Car(this: { brand: string }, car: { name: string }) {
    console.log(this.brand);  // ✅ TypeScript knows this has 'brand'
    console.log(car);
}

// Call with explicit 'this'
Car.call({ brand: 'Toyota' }, { name: 'BMW' });
// Output:
// Toyota
// { name: 'BMW' }

Solution 3: Don't Use this at All

If you don't actually need this, remove it:

function Car(car: { name: string }) {
    // console.log(this);  // ← Remove this line
    console.log(car);
}

console.log(Car({ name: 'BMW' }));
// Output: { name: 'BMW' }

This is the simplest fix if you're not using this.

Including and Excluding Files in TypeScript Configuration

Overview

When you run tsc, TypeScript needs to know which files to compile and which files to ignore. You control this through three configuration properties in tsconfig.json: 

{
  "files": [],
  "include": [],
  "exclude": []
}

1. The Three Properties Explained

Property Purpose When to Use
files Explicitly list exact files to compile Small projects, specific entry points
include Use patterns to select files to compile Most projects (wildcards)
exclude Use patterns to ignore files Exclude tests, node_modules, output
Key Rule

Final file list = (files + include) - exclude

2. files – Explicit File List

Definition: An exact list of file paths that must be compiled. Only these files will be processed.

Syntax:

{
  "files": [
    "src/index.ts",
    "src/app.ts",
    "src/utils/helper.ts"
  ]
}

Use Cases:

✅ When to use files:

  • Very small projects with few files
  • You want to compile specific entry points
  • Build tools like Webpack that handle dependencies

❌ When NOT to use files:

  • Large projects with many files (too much typing)
  • Projects that frequently add/remove files

Example:

{
  "files": [
    "src/main.ts",
    "src/worker.ts"
  ],
  "compilerOptions": {
    "outDir": "./dist"
  }
}

Result: Only src/main.ts and src/worker.ts are compiled. Any other .ts files are ignored.

3. include – Pattern-Based File Selection

Definition: Uses glob patterns (wildcards) to specify which files to compile.

Syntax:

{
  "include": [
    "src/**/*.ts",
    "src/**/*.tsx",
    "types/**/*.d.ts"
  ]
}

Glob Patterns Explained:

Pattern Meaning Example
* Matches any characters (except /) *.ts → app.ts, main.ts
** Matches any subdirectories src/**/*.ts → any .ts in src or subfolders
? Matches exactly one character file?.ts → file1.ts, fileA.ts
[abc] Matches one character in set file[1-3].ts → file1.ts, file2.ts

Common include Patterns:

{
  "include": [
    // All TypeScript files in src folder and subfolders
    "src/**/*.ts",
    
    // All TypeScript React files
    "src/**/*.tsx",
    
    // All declaration files in types folder
    "types/**/*.d.ts",
    
    // Only specific file types
    "src/**/*.{ts,tsx}",
    
    // Files in root src only (not subfolders)
    "src/*.ts"
  ]
}

Use Cases:

✅ When to use include:

  • Most TypeScript projects
  • Projects with organized folder structures
  • When you want to compile everything in a directory

❌ When NOT to use include:

  • When you need to compile only specific files
  • When you have many files you want to exclude (use exclude instead)

4. exclude – Pattern-Based File Exclusion

Definition: Specifies files to remove from the compilation (after files and include are applied).

Syntax:

{
  "exclude": [
    "node_modules/**/*",
    "dist/**/*",
    "**/*.test.ts",
    "**/*.spec.ts"
  ]
}

Common Exclude Patterns:

{
  "exclude": [
    // Always exclude dependencies
    "node_modules/**/*",
    
    // Exclude output folders
    "dist/**/*",
    "build/**/*",
    "out/**/*",
    
    // Exclude test files
    "**/*.test.ts",
    "**/*.spec.ts",
    "**/__tests__/**/*",
    
    // Exclude specific files
    "src/legacy/**/*",
    "src/experimental/**/*",
    
    // Exclude config files
    "*.config.js",
    "*.config.ts"
  ]
}

Use Cases:

✅ When to use exclude:

  • Exclude node_modules (always do this!)
  • Exclude test files from production builds
  • Exclude output folders
  • Exclude experimental/legacy code

❌ When NOT to use exclude:

  • When you want to exclude most files (use include instead)
  • When you want to exclude specific files (use files instead)

5. Important Behaviors & Rules

Rule 1: Default Behavior
If no files or include are specified, TypeScript compiles all .ts and .tsx files in the project directory and subdirectories, excluding those matched by exclude. 

{
  // No files/include
  "compilerOptions": { ... }
  // Compiles ALL .ts/.tsx files in project!
}

Rule 2: exclude Defaults
If you don't specify exclude, TypeScript defaults to: 

{
  "exclude": ["node_modules", "bower_components", "jspm_packages"]
}

Rule 3: exclude Does NOT Override files
If you explicitly list a file in files, it will be compiled even if it matches patterns in exclude: 

{
  "files": ["src/legacy/broken.ts"],  // ← This WILL be compiled
  "exclude": ["src/legacy/**/*"]       // ← Even though this excludes it
}

Rule 4: include + exclude Example

{
  "include": ["src/**/*"],
  "exclude": ["src/**/*.test.ts", "src/experimental/**/*"]
}

Result: All .ts files in src are compiled EXCEPT:

  • Any file ending with .test.ts
  • Any file inside src/experimental/ folder

Understanding the rootDir Error - Simplified

When I set the files property with "outDir": "./dist", the compiler shows this error: 

{
  "files": ["./src/sub.ts"],
  "compilerOptions": {
    "outDir": "./dist"
  }
}

The error: "The common source directory of 'tsconfig.json' is './src'. The 'rootDir' setting must be explicitly set to this or another path to adjust your output's file layout. Visit https://aka.ms/ts6 for migration information."

However, the error disappears when I delete the files property.

The Problem in Plain English

You told TypeScript:

  • "Compile this one file: ./src/sub.ts"
  • "Put the output in: ./dist"

TypeScript got confused and asked:
"Where should I put the output file?" 

Option A: ./dist/sub.js     (just the filename)
Option B: ./dist/src/sub.js  (keep the folder structure)

TypeScript doesn't know which you want, so it throws an error.

Why the Error Disappears Without files

When you have MULTIPLE files:

{
  "include": ["src/**/*.ts"],  // Many files in src folder
  "outDir": "./dist"
}

TypeScript looks at ALL your files and thinks:

  • "All files are under src/ folder"
  • "So src/ must be the root"
  • "I'll remove src/ from the path"

Result:

src/sub.ts       →  dist/sub.js
src/utils/helper.ts  →  dist/utils/helper.js

TypeScript can GUESS the root because it sees a pattern.

When you have ONE specific file:

{
  "files": ["./src/sub.ts"],  // Only ONE file
  "outDir": "./dist"
}

TypeScript looks at your ONE file and thinks:

  • "I only have one file"
  • "Is src/ the root?"
  • "Or is . (project root) the root?"
  • "I can't guess! You tell me!"

Result: ❌ ERROR

Simple Fixes

Fix 1: Tell TypeScript the Root Directory

{
  "compilerOptions": {
    "rootDir": "./src",  // ← ADD THIS ONE LINE
    "outDir": "./dist"
  },
  "files": ["./src/sub.ts"]
}

Now TypeScript knows:

  • Root = src/
  • Input = src/sub.ts
  • Remove src/ → sub.ts
  • Output = dist/sub.js

Fix 2: Don't Use files - Use include Instead

{
  "compilerOptions": {
    "outDir": "./dist"
  },
  "include": ["./src/sub.ts"]  // ← Same file, different property
}

Why this works: TypeScript assumes include files are under a common root.

What is tsc --init?

Definition: tsc --init is a command that automatically creates a tsconfig.json file with default configuration for your TypeScript project.

It saves you from: Writing tsconfig.json from scratch.

How to Use It

Step 1: Install TypeScript

npm install -g typescript
# OR (if using locally)
npm install --save-dev typescript

tsc --init

  esModuleInterop: true
  skipLibCheck: true
  forceConsistentCasingInFileNames: true

Statically vs Dynamically Typed Languages - Complete Guide

1. Clear Definitions

Statically Typed Language

Definition: A language where variable types are known at compile time (before the code runs). The type of a variable is fixed and cannot change.

Key characteristics:

  • Types are checked during compilation
  • Variables have a fixed type throughout their lifetime
  • Type errors are caught before the program runs
  • You must declare types explicitly (or compiler infers them)

Dynamically Typed Language

Definition: A language where variable types are determined at runtime (while the code is running). The type of a variable can change during execution.

Key characteristics:

  • Types are checked during execution
  • Variables can change type at any time
  • Type errors are caught during runtime
  • Types are determined by the value currently assigned

Quick Visual Comparison

┌─────────────────────────────────────────────────────────────────────┐
│                    STATICALLY TYPED (TypeScript)                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  let name: string = "Arman";   // Type is FIXED                   │
│  name = "Ali";                 // ✅ OK - still string            │
│  name = 25;                    // ❌ ERROR at COMPILE TIME        │
│                                                                     │
│  Type is checked BEFORE the program runs                          │
│  Error caught by developer, not user                              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                    DYNAMICALLY TYPED (JavaScript)                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  let name = "Arman";          // Type is STRING                   │
│  name = "Ali";                // ✅ OK - still string             │
│  name = 25;                   // ✅ OK - type CHANGED to number   │
│  name = true;                 // ✅ OK - type CHANGED to boolean  │
│                                                                     │
│  Type is checked DURING runtime                                   │
│  Error might reach the user if not handled                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

3. Detailed Examples

STATICALLY TYPED (TypeScript)

// Type is DECLARED and FIXED
let name: string = "Arman";
let age: number = 25;
let isActive: boolean = true;

// ✅ These work (same type)
name = "Ali";
age = 30;
isActive = false;

// ❌ These FAIL at COMPILE TIME
name = 42;          // Error: Type 'number' is not assignable to type 'string'
age = "twenty";     // Error: Type 'string' is not assignable to type 'number'
isActive = "yes";   // Error: Type 'string' is not assignable to type 'boolean'

// Function parameters are typed
function greet(name: string): string {
    return "Hello " + name;
}

greet("Arman");     // ✅ OK
greet(25);          // ❌ ERROR: Argument of type 'number' is not assignable to parameter of type 'string'

DYNAMICALLY TYPED (JavaScript)

// Type is INFERRED and can CHANGE
let name = "Arman";   // Type is string
name = "Ali";         // ✅ Still string
name = 42;            // ✅ Now number!
name = true;          // ✅ Now boolean!
name = { value: 1 };  // ✅ Now object!

// Function parameters have no types
function greet(name) {
    return "Hello " + name;
}

greet("Arman");   // ✅ OK - "Hello Arman"
greet(25);        // ✅ OK - "Hello 25" (works, but maybe unexpected!)
greet(true);      // ✅ OK - "Hello true"

// Bug only appears at RUNTIME
function add(a, b) {
    return a + b;
}

add(5, 10);       // ✅ 15 (number)
add("5", 10);     // ✅ "510" (string concatenation - unexpected!)
add({}, []);      // ✅ "[object Object]" (nonsense - unexpected!)
// No compile-time error. Bug reaches production!

Strongly vs Weakly Typed Languages - Complete Guide

1. Clear Definitions

Strongly Typed Language

Definition: A language that strictly enforces type rules and does not allow implicit type conversions (type coercion) between different types.

Key characteristics:

  • Types are strictly enforced
  • Cannot mix types in operations without explicit conversion
  • Type errors are thrown when operations are invalid
  • No automatic type coercion (conversion)

Weakly Typed Language

Definition: A language that allows implicit type conversions (type coercion) between different types automatically.

Key characteristics:

  • Types are loosely enforced
  • Can mix types in operations - language automatically converts
  • Rarely throws type errors
  • Automatic type coercion happens behind the scenes

2. Critical Difference: Type Coercion

What is Type Coercion?

Definition: The automatic conversion of a value from one type to another by the language, without the programmer explicitly requesting it. 

┌─────────────────────────────────────────────────────────────────────┐
│                    TYPE COERCION EXPLAINED                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  In WEAKLY typed languages:                                        │
│                                                                     │
│  5 + "5"  →  "55"    (number coerced to string)                   │
│  5 * "5"  →  25       (string coerced to number)                   │
│  "5" - 2  →  3        (string coerced to number)                   │
│  true + 1 →  2        (boolean coerced to number)                  │
│                                                                     │
│  In STRONGLY typed languages:                                      │
│                                                                     │
│  5 + "5"  →  ❌ ERROR (can't mix number and string)               │
│  5 * "5"  →  ❌ ERROR (can't mix number and string)               │
│  "5" - 2  →  ❌ ERROR (can't mix string and number)               │
│  true + 1 →  ❌ ERROR (can't mix boolean and number)              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

3. Detailed Examples

STRONGLY TYPED (TypeScript)

// In TypeScript, operations between different types FAIL

// Number + String
let num: number = 5;
let str: string = "10";
let result = num + str;  // ❌ ERROR: Operator '+' cannot be applied to types 'number' and 'string'

// Number + Boolean
let bool: boolean = true;
let result2 = num + bool;  // ❌ ERROR: Operator '+' cannot be applied to types 'number' and 'boolean'

// String - Number
let result3 = str - num;   // ❌ ERROR: The left-hand side of an arithmetic operation must be of type 'any', 'number', 'bigint' or an enum type

// Comparison between different types
let isEqual = (num === str);  // ✅ Allowed (strict equality), but always false
let isEqual2 = (num == str);  // ❌ ERROR: This condition will always return false since the types 'number' and 'string' have no overlap

// MUST EXPLICITLY CONVERT
let explicitConversion: number = num + parseInt(str);  // ✅ 15
let explicitConversion2: string = num.toString() + str;  // ✅ "510"

// All conversions must be explicit
let explicitBoolean: number = num + (bool ? 1 : 0);  // ✅ 6

WEAKLY TYPED (JavaScript)

// In JavaScript, type coercion happens AUTOMATICALLY

// Number + String = String (number coerced to string)
let num = 5;
let str = "10";
let result = num + str;  // ✅ "510" (no error!)

// Number + Boolean = Number (boolean coerced to number)
let bool = true;
let result2 = num + bool;  // ✅ 6 (true becomes 1)

// String - Number = Number (string coerced to number)
let result3 = str - num;   // ✅ 5 ("10" becomes 10)

// String * Number = Number (string coerced to number)
let result4 = str * num;   // ✅ 50 ("10" becomes 10)

// Comparison with coercion
let isEqual = (5 == "5");       // ✅ true ("5" coerced to number 5)
let isEqual2 = (5 === "5");     // ✅ false (strict equality, no coercion)

// Empty array to number
let result5 = [] + 5;          // ✅ "5" (empty array becomes empty string)
let result6 = [] - 5;          // ✅ -5 (empty array becomes 0)

// Unexpected results!
let result7 = "5" - "2";        // ✅ 3 (both strings coerced to numbers)
let result8 = "5" + "2";        // ✅ "52" (both are strings, no coercion needed)
let result9 = "5" - "hello";    // ✅ NaN (can't coerce "hello" to number)

4. The Dangerous Side of Weak Typing

Real-world bugs caused by weak typing:

function calculateTotal(price, quantity) {
    return price * quantity;
}

// During testing:

// Production: API returns price as string "$10"

} else {
    console.log("Minor");

    console.log("Adult");
} else {
    console.log("Minor");
}

7. TypeScript: Strong Typing on Top of Weak JavaScript

TypeScript makes JavaScript strongly typed while compiling to weakly typed JavaScript: 

// TypeScript (Strong):
let value: string = "5";
let num: number = 10;
let result = value + num;  // ❌ COMPILE ERROR
// "Types 'string' and 'number' have no overlap"

// This TypeScript compiles TO JavaScript (Weak):
// After compilation:
let value = "5";
let num = 10;
let result = value + num;  // ✅ "510" (this is what actually runs!)
// The TypeScript error is caught BEFORE the code runs

Key insight: TypeScript adds strong typing DURING DEVELOPMENT, but JavaScript (the runtime) is still weakly typed.

Top and Bottom Types in TypeScript: any, unknown, never

1. What Are Top and Bottom Types?

Top Type

Definition: A type that can hold any value from any other type. Every other type is assignable to a top type.

Bottom Type

Definition: A type that can hold no values at all. No value exists of a bottom type. 

┌─────────────────────────────────────────────────────────────────────┐
│                    TYPE HIERARCHY                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│                     ┌─────────────┐                                │
│                     │    any      │  ← TOP TYPE                    │
│                     │  unknown    │  ← TOP TYPE                    │
│                     └──────┬──────┘                                │
│                            │                                        │
│            ┌───────────────┼───────────────┐                       │
│            │               │               │                       │
│        ┌───▼───┐     ┌─────▼─────┐   ┌─────▼─────┐               │
│        │string │     │  number   │   │ boolean  │                │
│        └───┬───┘     └─────┬─────┘   └─────┬─────┘               │
│            │               │               │                       │
│            └───────────────┼───────────────┘                       │
│                            │                                        │
│                     ┌──────▼──────┐                                │
│                     │    never    │  ← BOTTOM TYPE                 │
│                     └─────────────┘                                │
│                                                                     │
│  Direction: Everything flows DOWN from top to bottom              │
│  • any/unknown can hold anything (they're at the top)             │
│  • never can hold nothing (it's at the bottom)                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

2. The any Type (Top Type)

Definition

any: A type that disables all type checking. It can hold any value, and you can do anything with it. It's the escape hatch from TypeScript's type system.

Characteristics:

  • Can hold any value (string, number, object, etc.)
  • Can call any method on it
  • Can assign it to anything
  • No type safety - like using plain JavaScript

Examples:

// any can hold ANY value
let data: any = "Hello";
data = 42;           // ✅ Allowed
data = true;         // ✅ Allowed
data = { name: "John" };  // ✅ Allowed
data = [1, 2, 3];    // ✅ Allowed

// any can call ANY method (even if they don't exist)
let value: any = "Hello";
value.toUpperCase();     // ✅ Works (string method)
value.push(5);           // ✅ No error! But will crash at runtime
value.nonExistent();     // ✅ No error! Will crash at runtime
value + 5;               // ✅ Works

// any can be assigned to ANYTHING
let value2: any = "Hello";
let str: string = value2;      // ✅ Allowed
let num: number = value2;      // ✅ Allowed (dangerous!)
let bool: boolean = value2;    // ✅ Allowed (dangerous!)

// any disables ALL type checking
function process(data: any): any {
    // TypeScript trusts you know what you're doing
    return data.whatever.method();
}

When to Use any:

Use Case Example
Migration from JavaScript Gradually adding types to old code
Third-party libraries without types Working with untyped libraries
Dynamic content JSON responses with unknown shape
Testing/mocking Quick prototypes

When NOT to Use any:

// ❌ BAD: Using any when you know the type
let name: any = "Arman";  // Should be: string

// ❌ BAD: Using any in function signatures
function add(a: any, b: any) {  // Should have proper types
    return a + b;
}

// ❌ BAD: Using any for objects
let user: any = { name: "Arman", age: 25 };  // Should have interface

3. The unknown Type (Top Type)

Definition

unknown: A type-safe version of any. It can hold any value, but you cannot do anything with it until you narrow down the type.

Characteristics:

  • Can hold any value (like any)
  • Cannot call methods or properties on it
  • Cannot assign it to anything except any or unknown
  • Must narrow the type before using it
  • Type-safe version of any

Examples:

// unknown can hold ANY value (like any)
let data: unknown = "Hello";
data = 42;           // ✅ Allowed
data = true;         // ✅ Allowed
data = { name: "John" };  // ✅ Allowed
data = [1, 2, 3];    // ✅ Allowed

// BUT you CANNOT do anything with unknown
let value: unknown = "Hello";
value.toUpperCase();     // ❌ ERROR: Object is of type 'unknown'
value.push(5);           // ❌ ERROR: Object is of type 'unknown'
value + 5;               // ❌ ERROR: Object is of type 'unknown'

// unknown CANNOT be assigned to anything except any/unknown
let value2: unknown = "Hello";
let str: string = value2;      // ❌ ERROR: Type 'unknown' is not assignable to type 'string'
let num: number = value2;      // ❌ ERROR: Type 'unknown' is not assignable to type 'number'

// Must NARROW the type before using
function process(data: unknown) {
    // ❌ Can't use directly
    // console.log(data.name);
    
    // ✅ Must check the type first
    if (typeof data === "string") {
        console.log(data.toUpperCase());  // ✅ Now it's safe
    }
    
    // ✅ Or use type narrowing with typeof
    if (typeof data === "number") {
        console.log(data + 5);  // ✅ Now it's safe
    }
    
    // ✅ Or use a type guard
    if (isUser(data)) {
        console.log(data.name);  // ✅ Now it's safe
    }
}

function isUser(obj: any): obj is { name: string; age: number } {
    return obj && typeof obj.name === "string" && typeof obj.age === "number";
}

4. The never Type (Bottom Type)

Definition

never: A type that represents values that never occur. It's the type of functions that never return or variables that can never have a value.

Characteristics:

  • No value can be of type never
  • Used for functions that always throw or never return
  • Used for exhaustiveness checking
  • It's the bottom type - nothing can be assigned to it

Examples:

// Function that always throws (never returns)
function throwError(message: string): never {
    throw new Error(message);
    // Nothing after this point
}

// Function that never returns (infinite loop)
function infiniteLoop(): never {
    while (true) {
        // Runs forever, never returns
    }
}

// Function that always exits the process
function exit(): never {
    process.exit(1);
    // Never reaches here
}

// NEVER can be used for exhaustiveness checking
type Color = "red" | "green" | "blue";

function getColorCode(color: Color): string {
    switch (color) {
        case "red":
            return "#FF0000";
        case "green":
            return "#00FF00";
        case "blue":
            return "#0000FF";
        default:
            // If we add a new color, this will catch it
            const exhaustiveCheck: never = color;
            return exhaustiveCheck;
    }
}

// If you add "yellow" to Color, TypeScript will show error
// because yellow is not handled and would be assigned to never
